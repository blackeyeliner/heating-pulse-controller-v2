# 0.1.0b26 — Stop diagnostic reads from interrupting healthy heating

Beta25 could lose a fast Zigbee2MQTT response because Home Assistant queues MQTT subscriptions instead of waiting for broker acknowledgement. A periodic diagnostic timeout then unnecessarily closed the valve, abandoned calibration and entered reconnection.

The response subscription now stays active for the integration entry's lifetime. It is registered before awaiting retained bridge metadata, crossing the broker subscription queue before sending the first raw read. Every request still uses a new transaction ID and validates its response bytes; retained, unrelated, cancelled and late replies cannot confirm a later request. Unload removes the listener and pending transactions.

A missing periodic response now retries after five seconds without interrupting the original pulse, but only if the previous successful pair is at most180 seconds old and the current entity limits still agree with it. Two consecutive missed replies are tolerated. A third miss, conflicting feedback or an invalid response closes the valve and enters the existing ten minute-spaced reconnection probes. Command completion still requires fresh proof; real mismatches retain the safe correction path. Diagnostic warnings include the transaction ID, and Phase exposes consecutive misses and total periodic timeouts.

The original pulse deadline is unchanged, including during retries. Existing maximum-opening settings, recovery timing, window policy, thermostat requests, frost protection and emergency reserve settings are preserved. No backup-climate commands are added.

Restart Home Assistant after updating. A delayed-subscription/fast-reply regression test fails against beta25 and passes with this release. Read-only real-device checks also exercised the new reader through the HA MQTT interface; they do not establish long-term reliability or physical water flow.
