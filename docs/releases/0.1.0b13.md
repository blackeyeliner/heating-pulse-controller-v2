# Beta13: delayed valve emergency confirmation

Beta13 adds a confirmation period before declaring a valve communication failure. Publication and installation authorised on2026-10-19.

A transient MQTT/Zigbee infrastructure restart now starts a persisted valve-reconnecting state. Normal openings are inhibited. Probe at +60 seconds, then at least60 seconds between starts, ten attempts total; initial error is not counted. A probe repeats safe closed-limit commands and waits for a fresh non-retained MQTT closed-limit message on the selected valve's discovery state topic. Cached HA values/retained MQTT state are insufficient. Available TRV/limit entities are also required.

Successful reconnection clears suspicion and automatically resumes a controller that remained enabled in this running session, through current demand/cooling/reporting/ownership rules. Manual disable is preserved. Reload/restart preserves timing/count but never restores ordinary enabled state. Legacy-writer ownership pauses probes. There is no burst catch-up after downtime, so the nominal ten-minute window can extend if HA is stopped or commands/ownership delay attempts.

The tenth failed probe confirms actuator_error and invokes the existing durable phone/all-selected-AC emergency path. Existing confirmed emergencies are not downgraded or reset. Shutdown-close failures also enter persisted suspicion. Tests cover boundary scheduling, recovery on the last attempt, manual off, real Store reload, missed ticks, guard ownership, broken persistence, metadata binding and stale/retained/malformed MQTT feedback.

Existing confirmed incidents are preserved during upgrade; clearing them is a separate explicit action. The MQTT probe uses HA2026.9.3 discovery diagnostic metadata and must be checked against future HA upgrades. It confirms a fresh logical device-state reply, not physical stem movement or water flow.
